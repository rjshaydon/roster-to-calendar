## Confirmed issues fixed locally

1. **Old authentication proof could outlive a password change.** Session revocation alone did not prevent a provider reply already in flight from issuing a fresh session afterward. Migration 0049 adds a credential version, an exclusive pending password-operation identity and atomic session revocation. Session issuance and hash retirement check the exact version/operation. Pending operations cannot issue sessions, including from a proof obtained during the mutation. Old-password compatibility for non-cohort legacy users also closes when an authorized reset/upgrade is pending.
2. **A shared cookie could change before another tab received notification.** Cookie requests now carry an expected-account assertion. The server checks it before returning state or performing account/session actions; the assertion never grants authority. Explicit login/signup/reauthentication/password-change responses have intent/generation fences. A stale successful authentication response is discarded and its cookie is cleaned up only under its exact account expectation, protecting a newer different account. Old app login failure/continuation code also checks its view transition before clearing the newer selection.
3. **Outstanding reset/invitation links survived password changes.** The credential-version trigger invalidates issued email challenges and unconsumed invitations. A challenge already being processed must still win the credential-version CAS, so it cannot cross a concurrent password change using a newer account version. These optional email paths remain disabled in the rollout configuration.
4. **Provider-incompatible legacy passwords led to a generic failure.** Creation policy rejection or an existing password exceeding the provider's 72-byte boundary now offers a stronger replacement inline, only after valid old-password proof. No confirmation email is needed. Normal compatible existing passwords are retained. New/replacement passwords require at least 12 characters and respect the provider's UTF-8 byte bound; passwords are never silently truncated. Replacement credentials go only to explicit authentication, not routine state/calendar requests or browser persistence. Definite policy rejection cancels the operation safely and can retain the current browser with an exactly version-bound cookie.
5. **Native D1 trigger counts differed from local direct-row counts.** The first native test returned `auth-password-pending` after a successful atomic update because D1 counted trigger side effects. The admission is a uniquely keyed CAS that can update at most one direct row; it now accepts a positive native count while zero remains closed. A dedicated SQLite test models total trigger changes, and the corrected native probe passes. This was an availability defect caught before activation, not a successful unauthorized login.

## Interrupted password operations

A pending target stores a temporary server-keyed HMAC tied to account, exact provider UUID and operation ID. It is not a primary password hash, session token or password substitute. It cannot be tested offline from a D1-only read without the server secret. It is cleared on completion/cancellation. Supabase remains the actual password verifier/storage provider.

For a lost response, the user can sign in using the intended new password only when Supabase verifies that exact password for the reserved account. The pending target and version prevent another password from completing it. No uncertain provider password write is automatically repeated: a late identical write could otherwise overwrite a subsequent password change. Before a fresh mutation, the code checks whether the target already works and avoids a redundant write. Definitive policy rejection/no-write failure can cancel; timeouts or ambiguous outcomes retain the fence.

If an ambiguous request never applied and the new password still cannot be verified, the operation stays locked and needs owner-assisted resolution. Do not clear the fence merely to make an old password work or blindly retry a provider mutation. Verify the remote operation's outcome/audit before an explicit reviewed recovery. The same caution applies to out-of-band provider administration. This exceptional recovery remains an operational acceptance item, not an excuse to restore weak hashes.

The temporary HMAC currently derives from the encrypted provider secret with domain separation. Before rotating that secret, resolve pending operations where possible. An urgent rotation can require owner-assisted resolution of pending targets; it must never reopen old sessions. A stable independent operation key can be considered during staging if rotation-independent recovery is required.
