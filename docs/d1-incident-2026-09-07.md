# D1 quota incident — 7 September 2026

## Confirmed impact

The Workers Free account exhausted its D1 row-read allowance and ordinary users
could no longer log in or use the application. No paid-plan escape route is
available.

## Account-wide Analytics evidence

Read-only GraphQL Analytics, collected after the incident without contacting
D1, reported:

- Production database: 9,064,320 rows read, 1,550 rows written, 2,456 read
  queries and 213 write queries from 00:00 through approximately 06:30 UTC;
- Preview database: no reported usage; and
- query fingerprints: 837,929 rows read and 510 rows written in total.

The 8,226,391-row difference between the account metric and query fingerprints
is unexplained and blocks rollout.

Normal preceding hours ranged from approximately 5,000 to 175,000 reads. The
incident is therefore a discrete 15-minute Production burst, not ordinary
steady traffic.

## Attribution established

- GitHub roster-processing automation did not run during the burst.
- Preview recorded no usage.
- The bootstrap inspection workflows ran at 04:53 and 04:55, after the burst.
  They requested no execution and cannot be its cause.
- The visible expensive fingerprints include eight active-roster file listings
  with correlated event/doctor counts (303,072 reads) and repeated global state
  reads. Those visible operations are wasteful but do not explain the account
  total.
- `3ee4bff` was merged to `main` at 04:18 UTC and Production/Preview deployments
  followed before the application was reopened. Remote migration and deployment
  activity also occurred in the surrounding interval. Temporal correlation is
  not proof of which operation produced the unattributed reads.

Pages Functions Analytics independently recorded a Production request storm in
the same three buckets:

| UTC bucket | Production requests | D1 rows read |
| --- | ---: | ---: |
| 04:35–04:39 | 151 | 1,679,352 |
| 04:40–04:44 | 79 | 3,718,449 |
| 04:45–04:49 | 165 | 3,464,572 |

The preceding Production buckets contained only 4–10 requests each. Preview
had three requests at 04:40 and two at 04:45, with no D1 usage attributed to
its database. The damaging event was therefore a Production request storm,
not ordinary traffic or one bootstrap request. Historical Pages Analytics does
not expose request paths, and D1 query fingerprints omit most of the associated
row reads, so the precise initiating browser/API loop remains unproven.

## Current conclusion

The incident source is narrowed to a Production request storm between 04:35 and
04:49 UTC. Cloudflare's `d1QueriesAdaptiveGroups` data does not expose enough
rows to attribute the dominant operation or its route. Do not claim that the
bootstrap canary, Preview or GitHub automation caused it, and do not claim that
the precise request loop or SQL is known.

All optional Production functionality remains paused. The next reset-day work
is passive observation through account-wide Analytics. No D1 request is used
as a probe. Any aggregation discrepancy or unattributed usage returns `STOP`.
